## Premissas e limites

- A unidade editável será um documento JSON hierárquico com um nó raiz e filhos ordenados; o domínio de cada nó (campos específicos, comandos ou metadados) ainda deve ser confirmado pelo PO/HRS.
- O primeiro corte terá uma única área de edição e uma árvore navegável; colaboração multiusuário, autenticação, sincronização remota, versionamento no servidor e anexos ficam fora do escopo.
- JSON Schema será versionado dentro do projeto e usado como contrato de validação; a biblioteca de validação pode ser empacotada localmente ou adicionada por CDN apenas se a política do projeto permitir.
- `localStorage` será a persistência primária do MVP. Limite de quota, limpeza do navegador e privacidade devem ser comunicados na UI.
- Importação e exportação usarão JSON UTF-8; arquivos inválidos nunca substituirão o estado atual sem confirmação e validação bem-sucedida.

## Modelo de dados recomendado

```json
{
  "schemaVersion": "1.0.0",
  "documentId": "uuid",
  "updatedAt": "2026-09-24T00:00:00.000Z",
  "root": {
    "id": "root",
    "type": "root",
    "title": "Documento",
    "content": "",
    "children": [],
    "meta": {}
  }
}
```

Regras: `id` único no documento; `children` sempre array; ordem dos filhos significativa; `type` enum inicial definido no schema; `schemaVersion` permite migrações futuras; `updatedAt` atualizado somente na confirmação de uma transação. O schema deve impor profundidade máxima, limites de tamanho e tipos permitidos quando os valores de produto forem confirmados.

MVC não deve significar três globais: Model expõe estado/seletores/comandos; Controller traduz eventos em comandos; View recebe estado/props e atualiza DOM. O `main.js` injeta dependências e registra um único fluxo de renderização/atualização.

## Fluxos funcionais

1. Inicialização: carregar schema e estado padrão; ler envelope do `localStorage`; validar versão e documento; se inválido, preservar cópia de recuperação e iniciar estado seguro; renderizar e anunciar o resultado.
2. Edição: usuário seleciona nó/campo → controller valida intenção → comando produz próximo estado → validação incremental ou completa → histórico registra transação → persistência agenda gravação → view atualiza seleção, árvore, editor e status.
3. Undo/redo: comando confirmado entra em `past`; undo move o último estado/transação para `future`; redo retorna para `past`; nova alteração após undo limpa `future`; botões e atalhos refletem disponibilidade.
4. Importação: escolher arquivo → ler texto com limite → parsear JSON → normalizar/migrar versão → validar schema → confirmar substituição se houver alterações → criar ponto de histórico “importação” → persistir/renderizar.
5. Exportação: validar estado atual → serializar com indentação determinística → criar `Blob` → disparar download; se inválido, bloquear exportação e focar resumo de erros.

## Impactos e dependências

| Área | Impacto/dependência |
|---|---|
| Domínio | Necessita decisão dos tipos de nó, campos, regras de pai/filho e limites. O schema não deve ser inventado além do esqueleto proposto. |
| Frontend | Todos os arquivos serão novos; não há compatibilidade retroativa conhecida. |
| Persistência | Chave versionada, envelope com checksum opcional e política de recuperação; `localStorage` não é backup. |
| Bibliotecas | Validador JSON Schema é dependência técnica potencial. Preferir pacote local/reprodutível; CDN é fallback de protótipo e deve ser explicitamente aprovado. |
| Testes | Runner de navegador/Node deve ser escolhido. A lógica pura deve ser testável sem DOM; testes de acessibilidade exigem browser automatizado ou inspeção equivalente. |
| Deploy | Qualquer servidor de arquivos estáticos é suficiente; configurar headers CSP quando houver ambiente de publicação. |
| Produto | Textos de erro, rótulos, confirmação de substituição e limites visíveis precisam de revisão do PO. |

## Alternativas consideradas

### A — Estado imutável com snapshots completos

Mais simples e confiável para MVP: cada transação armazena estado anterior/próximo. Consome mais memória em documentos grandes, mas reduz a complexidade de inversão de operações.

### B — Histórico por patches/operadores inversos

Mais eficiente para documentos grandes, porém requer patches robustos para mover/remover nós, tratamento de IDs e migração de operações. Aumenta risco inicial.

### Recomendação

Adotar A no primeiro corte, com limite de snapshots e clone/serialização controlados. Encapsular a interface de `history` para permitir B posteriormente sem alterar controllers. Não adicionar framework ou backend sem decisão explícita.

## Riscos e mitigação

- Schema de domínio incompleto pode gerar modelo incompatível: bloquear campos de negócio em decisão pendente e entregar primeiro o esqueleto versionado.
- `localStorage` pode ser apagado ou exceder quota: capturar exceções, indicar “não persistido”, oferecer exportação manual e manter estado em memória.
- Undo/redo pode restaurar seleção incoerente: registrar seleção separadamente ou recalcular seleção pelo ID, com fallback para ancestral/raiz.
- JSON importado pode conter conteúdo malicioso: nunca usar `innerHTML`, `eval`, templates executáveis ou URLs não validadas; aplicar CSP na publicação.
- Re-renderização total pode ficar lenta: começar com renderização simples, medir, e separar atualização de árvore/editor se o volume justificar.
- Dependência via CDN pode quebrar offline/reprodutibilidade: preferir artefato local e fixar versão/integridade.
- Acessibilidade pode regredir com árvore customizada: usar semântica nativa quando possível, roving tabindex controlado e testes com teclado/leitor.
- Exportar estado inválido pode produzir arquivo inutilizável: bloquear exportação e exibir erros acionáveis.
- Corrupção de `localStorage`: validar envelope, usar chave de backup temporário e permitir “iniciar documento limpo” sem apagar silenciosamente o backup.
